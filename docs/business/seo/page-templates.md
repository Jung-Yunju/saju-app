# 검색 유입 페이지 설계 (P8-02)

> 작성: 사업기획·마케팅 담당 / 2026-11-27 / 상태: **제안**
> 구현은 프론트엔드(페이지)·백엔드(사이트맵 등)가 한다. 이 프로젝트의 Next.js는 알려진 버전과 다르므로 메타데이터·사이트맵 구현 전 `node_modules/next/dist/docs/`의 해당 안내를 먼저 읽는다.
> 말투·금지어: `docs/knowledge/voice-guide.md`. 키워드·우선순위: [keyword-plan.md](keyword-plan.md).

## 0. 공통 규칙

### 0-1. URL (제안, 영문 로마자 고정 — 한글 URL 인코딩 문제 회피)
| 유형 | 경로 | 예 |
|---|---|---|
| 도구 | `/free` | (프론트 구현 중) |
| 연도 운세 허브 | `/unse/{연도}` | `/unse/2027` |
| 띠×연도 | `/unse/{연도}/tti/{띠}` | `/unse/2027/tti/yang` |
| 일주 | `/ilju/{로마자}` | `/ilju/gapja`, `/ilju/eulyu`, `/ilju/byeongo` |
| 일간 | `/ilgan/{로마자}` | `/ilgan/gap` |
| 오행 | `/ohaeng/{오행}-{bujok|gwada}` | `/ohaeng/mok-bujok` |
| 용어 | `/yongeo/{slug}` | `/yongeo/daeun` |
- 천간 로마자: gap eul byeong jeong mu gi gyeong sin im gye. 지지: ja chuk in myo jin sa o mi sin yu sul hae. 일주 slug는 두 글자를 이어 붙인다(예 갑자 `gapja`, 병오 `byeongo`). 천간 신(辛)과 지지 신(申)은 소리가 같지만 일주 안에서 위치가 정해져 있어 slug가 겹치지 않는다. 표기는 구현 때 표 하나로 고정한다.
- **발음 주의(병신 일주)**: 병신(丙申)일주는 비하어와 소리가 같다(voice-guide §6). 페이지 제목·본문에는 반드시 "병신(丙申)일주"처럼 한자를 붙이고 말장난·인용을 하지 않는다. 검색어는 그대로 들어오므로 페이지는 만들되, 제목·메타 문구 표기는 연구소장·총괄실장이 확인한다. 같은 이유로 병(丙)과 신(辛)의 합은 "병신합"이라 쓰지 않는다.
- 연도·일주 페이지의 **정식(canonical) 주소는 하나**. 쿼리 파라미터(`?from=` 등)가 붙어도 `rel=canonical`은 깨끗한 주소.

### 0-2. 제목·메타 설명 규칙
| 항목 | 규칙 |
|---|---|
| title | 핵심 검색어를 **앞**에. 30자 안팎(검색 결과에서 잘리지 않도록, 일반 관행·추정). 끝에 ` | 할머니가 풀어 주는 사주` — 길면 브랜드를 뺀다 |
| meta description | 70~90자(모바일 기준 추정). 첫 문장에 검색어 답을 한 줄로. **단정·과장 금지**: "정확한", "100%", "적중", "무조건", "대박", "액운", "흉" 금지 |
| H1 | 페이지당 하나. title과 같은 뜻, 문장 말투는 평서. 할미 말투는 본문 첫 단락부터 |
| 날짜 | 본문 끝에 "처음 쓴 날 / 고친 날" 표시. 연도 페이지는 해마다 고친 날을 갱신 |
| 글쓴이 표시 | "할머니가 풀어 주는 사주 편집" + 감수 표시(명리학 연구소장 감수 완료 여부). 감수 전 원고는 게시하지 않는다 |
| 고지 문구 | 모든 풀이성 페이지 끝에 한 번: "옛 명리 이론으로 읽은 것이고, 앞날을 맞힌다고 증명된 것이 아닙니다. 재미와 자기 이해를 위한 참고 자료입니다." |

### 0-3. 행동 버튼(→ `/free`) 위치 — 모든 유형 공통 3곳
1. **첫 화면 안**(첫 단락 바로 아래): "내 여덟 글자 무료로 보기" — 생년월일을 바로 받는 **작은 입력 폼 또는 버튼**. 가입·로그인 없음을 한 줄로 밝힌다(사실이므로).
2. **본문 중간**(핵심 정의·일주 성격 풀이를 읽고 난 직후): 그 글 맥락에 맞춘 문구. 예) 용어 `대운` 끝: "내 대운은 언제 바뀌는지 보기".
3. **글 끝**: 다음에 읽을 글 + 같은 버튼.
- 버튼 문구는 **뭘 얻는지** 쓴다. "지금 확인하지 않으면 후회" 같은 공포 문구 금지.
- 모바일 하단 고정 버튼은 **쓰지 않는다**(본문을 가려 이탈이 늘 수 있으나 이번에 검증하지 못함 — A/B 후보로만 둔다).
- 링크에는 `?from=seo-{유형}-{slug}`를 붙여 어느 글에서 왔는지 측정(개인정보 아님). 생년월일은 어떤 분석 도구에도 보내지 않는다([measurement-plan.md](measurement-plan.md)).

### 0-4. 내부 링크 규칙
- 모든 페이지는 **위로**(인덱스·허브) 1개, **옆으로**(같은 유형 관련) 3~5개, **도구로**(`/free`) 최소 2개를 건다.
- 용어가 본문에 처음 나오면 용어 페이지로 링크(한 페이지에서 같은 용어는 첫 번째만).
- 앵커 텍스트는 설명적으로("대운 뜻 보기"). "여기 클릭" 금지.
- 고립 페이지 금지: 사이트맵과 인덱스 양쪽에서 닿아야 한다.
- 연도 허브 ↔ 일간 10 ↔ 일주 60 ↔ 용어는 아래 §1~§4의 연결표를 따른다.

### 0-5. 구조화 데이터 (적합한 것만)
| 유형 | 쓴다 | 이유 |
|---|---|---|
| `BreadcrumbList` | 모든 인덱스·상세 | 위치 정보. 위험 없음 |
| `Article`(또는 `WebPage`) + 게시·수정일 | 연도 허브·일주·용어 | 일반 정보 페이지 |
| `WebApplication` | `/free` 하나 | 무료 도구 설명 |
| `DefinedTerm`(+ `DefinedTermSet`) | 용어 사전 | 의미상 맞음. **검색 결과 효과는 보장 없음** — 구현 비용이 크면 생략 |
| `FAQPage` | **쓰지 않는다** | 구글은 2023-08부터 FAQ 리치 결과를 정부·건강 사이트로 제한했고, 검색 도구 결과상 이후 완전히 중단·지원 종료가 예고되었다(2026-05~06, 2차 보도 기준 — 출시 전에 구글 공식 문서로 재확인). 본문에 Q&A 절은 두되 마크업은 안 한다 |
| `HowTo`, `Review`, `Rating` | 쓰지 않는다 | 해당 없음·허위 평점 위험 |
- 구조화 데이터의 내용은 **화면에 보이는 내용과 같아야** 한다.

### 0-6. 색인 제어
- 원고가 감수 전·미완성인 페이지는 `noindex`(검색에 안 나옴)로 배포하거나 아예 배포하지 않는다. 사이트맵에도 넣지 않는다.
- 결과 화면(`/free` 결과, 개인 풀이)은 **noindex**. 개인 생년월일이 URL에 들어가지 않게 한다(공유 링크는 별도 설계).
- 사이트맵은 유형별로 나누고, 마지막 수정일을 실제 수정일로 적는다.

### 0-7. 성능·접근성(검색 품질에 영향, 일반 상식)
정적으로 미리 만들 수 있는 페이지(용어·일주·연도)는 서버에서 미리 생성해 첫 화면이 빨리 뜨게 한다. 이미지에는 대체 텍스트. 한자는 `<ruby>` 또는 괄호 병기(읽어 주는 도구가 헷갈리지 않게).

**검색의도**: 탐색. 대상 검색어: "갑자일주", "갑자일주 성격".
**원고 틀 = `content/seo/ilju/甲子.md`** (견본).

| 요소 | 규칙 |
|---|---|
| title | `갑자(甲子)일주 성격 — 물 위에 선 큰 나무 | 할머니가 풀어 주는 사주`(일주마다 다른 한 줄 별명) |
| 메타 | 일주 한자 + 한 줄 이미지 + 근거 글자 1개. 예: "갑자(甲子)일주는 일지 자(子)가 일간을 받쳐 주는 정인 구조예요. 겉과 속, 쓰는 법을 풀었어요." |
| 본문 섹션 | ① 한눈에(데이터 상자) ② 겉 / 속 / 이 사람을 여는 것 — 한 장면 비유 ③ 굳는 데는 왜 굳나 ④ 일지의 속사정(지장간) ⑤ 곁자리 일지와 부딪히거나 붙는 글자 ⑥ 같은 일간의 다른 일주와 다른 점(비교 3줄) ⑦ 올해·내년 이 일주에 닿는 글자(연도별 상자) ⑧ 내 사주로 확인(→ `/free`) ⑨ 이 글을 읽는 법(고지) |
| 행동 버튼 | ② 직후, ⑧, 글 끝 |
| 내부 링크 | 위: `/ilju` 인덱스·해당 `/ilgan/*`. 옆: 같은 일간 다른 일주 5개(예: 갑자→갑인·갑진…), 같은 일지 다른 일주는 링크 안 함(중복 방지). 용어: 일주·십성·공망·충 |
| 구조화 | BreadcrumbList, Article |

### 2-1. 60개가 서로 달라야 한다 — 중복 방지 규칙 (핵심)
검색엔진은 틀만 같고 단어만 바꾼 대량 페이지를 낮게 보거나 색인하지 않을 수 있다(일반 지침, 이번에 측정하지 못함 — 출시 후 서치콘솔 "색인 생성 여부"로 확인). 그래서 아래를 지킨다.
1. **고유 문장 비율**: 페이지 본문의 70% 이상은 그 일주에서만 나오는 문장. 틀(섹션 제목·고지·버튼)은 30% 이하.
2. **엔진 데이터 상자**(자동 생성, 정확성 보장): 일간 오행·음양, 일지 정기와 지장간, **일간 기준 일지 십성**, 월 계절 감각, 공망 지지 2개, 일지 충·합·형·파·해 상대. 60개 모두 조합이 다르다(일간 10 × 일지 12 중 60쌍).
3. **손으로 쓴 풀이**(②③⑥)는 근거 글자 공식으로: 어느 글자 → 이 사람에게 무엇 → 쓰는 법. 다른 일주에 붙여도 통하면 지운다(voice-guide §7). 비유(장면)는 60개 모두 다른 것으로, 같은 일간 6개 안에서 특히 겹치지 않게.
4. **⑥ 비교 3줄**은 같은 일간 6개 일주(예 갑자·갑인·갑진·갑오·갑신·갑술)와의 차이를 쓰므로 자연히 다르다.
5. **⑦ 연도 상자**는 일지×그해 지지 관계로 만든다. 12가지 지지 조합뿐이라 문장 틀이 같을 수 있으므로 **상자는 짧게(2~3문장)** 하고 페이지의 핵심 분량으로 삼지 않는다.
6. **유사도 검사**: 품질검증 담당자가 60개 간 본문 유사도(문장 단위 중복률) 점검 스크립트를 만든다. 기준(제안): 임의의 두 페이지 문장 중복 20% 미만, 한 페이지가 다른 어느 페이지와도 연속 3문장 이상 같지 않음.
7. **발행 방식**: 한꺼번에 60개를 열지 않는다. 견본 3 → 검증 후 12 → 서치콘솔에서 색인·노출을 보고 나머지를 순차 공개. 미완성은 `noindex`(§0-6).
8. 같은 십성 구조를 가진 일주가 여럿(예: 일지가 모두 "인성"인 일주들)이라도 **근거 글자·지장간·계절이 다르므로** 이 차이를 ② 첫 문장에 반드시 넣는다.
9. 일주 성격 설명은 **좋고 나쁨 판정·성별 구분·재물·결혼 단정 금지**(voice-guide §9).

## 4. 띠×연도 (`/unse/{연도}/tti/{띠}`)
**검색의도**: 시즌. 대상: "2027 양띠 운세".
- 경쟁이 가장 치열한 유형이며 경쟁 글은 띠 전체를 한 덩어리로 단정한다(관찰). 우리는 **띠(= 연지)와 그해 지지의 관계(충·합·형·파·해)** 라는 계산 가능한 사실을 중심에 둔다.
- **중요한 한계**: 띠는 태어난 해의 지지일 뿐 사주의 일부(연지)다. 같은 띠 사람 모두에게 같은 운을 단정하지 않는다는 점을 첫 단락에 쓴다.

| 요소 | 규칙 |
|---|---|
| title | `2027년 양띠 운세 — 정미년과 양띠(未)의 관계 | …` |
| 본문 섹션 | ① 이 띠가 어떤 지지인가(未, 오행) ② 그해 지지와의 관계(표, 사실) ③ 같은 띠도 사람마다 다른 이유(일간·일지 이야기) ④ 출생연도 표(입춘 이전 출생은 앞 띠 안내) ⑤ 내 사주로 보기(→ `/free`) ⑥ 다른 띠 보기 |
| 금지 | 띠별 점수·순위, 삼재, 사건 단정, 띠 궁합 성격 판정 |
| 중복 방지 | 12페이지 차이는 ②의 관계표와 ①이 만든다. ③ 이후 틀은 같으므로 **12개를 허브 1개 + 상세 12개로 하되 상세가 얇으면 허브에 합치는 쪽**을 검토. 출시 후 색인 상태를 보고 결정 |

## 5. 오행 부족·과다 (`/ohaeng/{오행}-{bujok|gwada}`) — P1
- 틀: ① 이 오행이 뜻하는 것 ② 개수를 어떻게 세는지(앱마다 다름) ③ 많을 때·없을 때 **작용**(성별·개운법 없음) ④ 없다고 나쁜 게 아닌 이유 ⑤ 내 오행 보기(→ `/free`).
- 10개 페이지의 ①③이 같은 틀이므로 유사 위험이 크다. 5개 오행 허브 + 부족/과다를 한 페이지에 두 절로 두는 **5페이지안**도 검토한다(대표 결정 불필요, 총괄실장·사업기획 판단).
