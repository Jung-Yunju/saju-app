## 검수 방법(실제로 한 것)

1. 이미 찍힌 스크린샷 21장(`um-pm-check/`)을 직접 열어 봤다.
2. 자동 검사 도구 `scripts/qa/visual-check.cjs`를 내가 다시 실행했다. 결과는 결함 0건, 종료 코드 0으로 보고와 같았다.
3. 독립 촬영·측정 스크립트 `scripts/qa/um-visual-review.cjs`(이번에 새로 작성)를 돌렸다. 촬영 범위와 측정 항목은 아래와 같다.
   - 결과 화면을 **끝까지(fullPage)** 찍었다. 「할미는 어떻게 알았을까?」 접기를 닫은 상태와 연 상태를 모두 찍었다.
   - 입력 화면은 책 쪽 안 스크롤을 끝까지 내리며 찍었다. 「한밤중」을 고른 상태와 가장 긴 시간대 이름을 고른 상태도 찍었다.
   - 측정 항목: 44px 미만 터치 대상, 16px 미만 본문 문단, 마지막 줄 외톨이, 줄바꿈 묶음에서 마지막 줄에 한 항목만 남는 경우.
   - 도구에 없는 조건 3개를 더했다.
     - `pz412-130`(317×704): 크롬 안드로이드가 글꼴 크기를 「페이지 확대」로 반영하면 CSS 폭이 줄어든다. 412px 화면을 130%로 확대한 것과 같은 조건이다.
     - `pz412-150`(275×610): 같은 방식으로 150% 확대한 조건이다.
     - `fold344`(344×882): 갤럭시 Z 폴드 덮개 화면에 가까운 크기다.
4. 보조 확인(스크립트는 임시 폴더에 있다)
   - 12개 시간대 이름 각각에 대해, 고른 값이 칸 안에 다 들어가는지 조건별로 쟀다.
   - 결과 화면 역할별 글자 크기를 실측했다.
   - 책 위에서 휠을 굴려 문서가 내려가는지 시험했다.
   - 화면의 모든 글자 덩어리가 안드로이드 「자동 글자 확대」 차단 장치(높이 상한) 안에 들어가는지 근사로 계산했다.
5. 모두 헤드리스 Chromium 흉내다. 실제 갤럭시 기기, 삼성 인터넷, 사파리에서는 측정하지 않았다(미검증 절 참고).

### 자동 검사 도구가 놓친 이유(도구 한계)

- 결과 화면은 첫 한 화면만 찍는다. 글자 검사도 닫힌 접기 안을 빼므로 「할미는 어떻게 알았을까?」 내용과 서가·끝부분은 사람이 본 적이 없었다.
- 「시진」 검사는 「한밤중 (자시)」 한 가지만 고른다. 더 긴 「오전 10시경 (사시)」 같은 이름은 고르지 않아 잘림(M4)을 놓쳤다.
- 「한 항목만 다음 줄」, 「마지막 줄 한 낱말」, 터치 대상 크기, 16px 미만 본문은 검사하지 않는다. 이번 지적의 대부분이 이 종류다.
- 115%·130% 조건은 칸 폭은 그대로 두고 글자만 키운다. 최신 크롬 안드로이드처럼 OS 글꼴 크기를 페이지 확대로 반영하면 화면 폭 자체가 줄어드는데, 이 경우는 다루지 않는다(아래 「글자 크기 키우기 대응 의견」 참고).
- 340px대 화면(폴드 덮개)이 없다.

## 글자 크기 키우기(text-size-adjust·글꼴 부스팅) 대응에 대한 의견

현재 코드는 세 가지로 대응한다.
- `html:has(.um-root) { text-size-adjust: 100% }`
- `.um-root`와 `.ub-book__content`에 `max-height: 1000000px` → 높이 상한이 있는 상자 안 글은 자동 확대하지 않는 엔진 규칙을 이용한다.
- 모든 크기를 rem으로 잡는다.

1. **자동 확대 차단 자체는 근거가 있다.** 근사 계산으로, 입력 화면 글자 덩어리 32/32개와 결과 화면 149/149개 모두 스크롤 상자를 만나기 전에 높이 상한이 있는 조상을 거친다. 따라서 Blink의 「높이 제한 상자 안은 자동 확대 안 함」 규칙이 그대로 동작한다면, 덩어리마다 배율이 달라지는 「제각각」 현상은 이 화면에서 꺼진다. 다만 이 판단은 내가 알고 있는 엔진 동작을 근거로 한 것이고, **실기기로 확인하지 않았다**.
2. **부작용: 사용자가 고른 큰 글씨가 이 화면에서 무시된다.** 설계 문서도 「WebView 앱의 textZoom은 이 화면에 적용되지 않는다」고 인정한다. 「기본 글자가 16~20px라 충분하다」는 논리는 큰 글씨가 꼭 필요한 사용자(노안·저시력)에게는 맞지 않는다. 주 고객층을 생각하면 접근성이 뒤로 가는 것이다. 덩어리마다 다른 배율을 막는 것과 사용자 배율을 통째로 버리는 것은 다른 일이다.
3. **최신 크롬 안드로이드는 다른 길로 갈 수 있다.** 크롬 측 공지에 따르면 안드로이드 크롬의 글자 확대는 데스크톱처럼 「페이지 확대」(OS 글꼴 크기 반영)로 바뀌는 중이다. 이 경우 위 장치와 상관없이 화면 전체가 확대되어 CSS 폭이 줄어든다(412px → 130%일 때 317px). 내가 추가한 `pz412-130/150` 조건이 이 경우에 가깝고, 바로 여기서 M4·M5가 크게 나타났다. 도구의 `a412-115/130`(글자만 키우고 칸 폭은 그대로)은 이 경로를 대표하지 못한다. 현재 기본값이 버전·설정마다 다르다는 자료도 있어(자료끼리 상충), 대표 기기에서 실제로 어떻게 되는지는 **미검증**이다.
4. **표준 쪽 대안을 검토하기를 권고한다.** 크롬은 `<meta name="text-scale" content="scale">`(OS 글꼴 배율을 rem에 반영하고 자동 확대를 끄는 명시적 선택)와 `env(preferred-text-scale)`를 제안·시험하고 있다. 이 화면은 이미 rem 체계라 잘 맞는다. 출시 상태와 지원 범위는 확인하지 못했다(문서 사이트 접속 불가). 엔진 내부 휴리스틱(`max-height` 핵)에 기대는 방식은 비공식 동작이라 엔진이 바뀌면 조용히 깨질 수 있다. 유지하려면 `docs/MAINTENANCE.md`에 근거와 재검 방법을 남겨야 한다.
5. **삼성 인터넷**의 자체 「텍스트 크기」 설정이 자동 확대 경로를 쓰는지 페이지 확대 경로를 쓰는지는 확인하지 못했다(**미검증**).
6. iOS 사파리에서 `text-size-adjust: 100%`는 가로 회전 때 글자가 저절로 커지는 것을 막는 용도로 타당하다.
7. 결론: 「같은 화면 안에서 크기가 제각각인 현상」을 끄는 목적에는 타당하다. 하지만 큰 글씨를 쓰는 사용자 대응으로는 불충분하다. 큰 글씨 사용자가 어느 경로로 오든 무너지지 않으려면 좁은 폭(275~320px)에서 쓰는 배치가 필요하다. 라벨을 값 위로 올리고, select 이름을 짧게 하거나 두 줄을 허용하고, 범례와 책등의 꺾임을 고치는 것이다.

## 대표에게 보여도 되는가: **예(조건부)**

- 이유: 대표가 지적한 「기본 글자 크기에서 같은 화면 안 글자 크기가 제각각」은 입력 화면에서 해소되었다. 역할별 크기가 5단계로 맞고, 원래 증상인 칸 안 숫자 잘림·겹침도 재현되지 않았다. 확인용 미리보기로 보여 주는 것은 괜찮다.
- 조건
  - ① 「수정 완료」가 아니라 「검수 중(수정 필요)」으로 보고한다.
  - ② 결과 첫 화면의 오행 범례 외톨이(M1)와 서가 책등의 「길」(M2)은 대표 눈에 바로 띌 수 있으므로 알려진 문제로 함께 알린다.
  - ③ 대표 휴대폰의 글꼴 크기 설정(기본인지, 크게인지)과 쓰는 앱(크롬·삼성 인터넷·Claude 앱)을 물어 확인한다. 큰 글씨라면 M4·M5(시간대 이름 잘림, 한 항목씩 떨어지는 줄)가 그대로 보일 것이다.
  - ④ 자동 검사 도구의 「결함 0건」은 위 한계 때문에 완료 근거로 쓰지 않는다.
